# A first launch that works offline

Status: design, 2026-10-27, for the owner's approval. The owner chose the scope in chat: when someone opens the
app with no signal, they should be able to look things up. Everything else here is my call and marked.

## Problem

On a first launch with no network the app stops at "Can't Reach the Server" and shows no tab, because it waits
for the verb data (`verbs.json`), which is only ever downloaded. The same is true of grammar, furigana and
words. Only `forms.json` has a bundled copy (#156), and the bundled counters copy added on 2026-10-27 cannot
help on its own, because the app never gets as far as the Counters tab. I confirmed this with a throwaway build
pointed at an unreachable host.

## Goals

- A first launch with no network opens the app and everything you look up works: the verb table, conjugations,
  Grammar, Counters, furigana, the form lookup, the word bank, and the widgets.
- The data you see is the data the app was built with; a sync replaces it when something newer arrives.
- No change to what a synced app does, and nothing that can show older data than the device already has.

## Non-goals

- Features that need the network (Refresh data, the first sync itself). They keep their current behaviour.
- Bundling anything other than the six data files (`verbs`, `grammar`, `furigana`, `words`, `counters`,
  `forms`; the last already is).
- Shrinking or compressing the data.

## Anti-goals

- A second code path that only runs offline and so is never exercised. The bundle must go through the same
  persistence and the same checks as synced data.
- Widgets or App Intents that are empty until the first download. They read the persisted store.
- A bundle that can drift from `data/`. A stale bundled copy must fail CI, as forms does.

## Approach

### The bundle is installed, not just read

At launch, for each data file, the store asks "is the bundled version newer than the last version synced on
this device?" If yes (including "nothing synced yet"), it **installs the bundled copy as if it had been
synced**: it persists the bundled data into the existing SwiftData store and records the bundled manifest as
synced. Then it loads and syncs exactly as it does today. Consequences:

- Widgets, App Intents, Spotlight and every screen see the same persisted data as always, with no new path.
- The sync service needs no change: a remote manifest equal to the recorded one is `.upToDate`, an older one is
  already rejected as a rollback, and a newer one is downloaded as usual.
- After an app update that ships newer data, the installed copy is replaced by the newer bundled one once,
  even before the first sync.
- The verb first-launch gate (`firstLaunchState`) is `.success` as soon as the bundle is installed. The
  "Can't Reach the Server" screen remains only for a missing or corrupt bundle.

This is the one decision that departs from the counters change made on 2026-10-27, which keeps the bundle in
memory only (so the Counters widget would stay empty). That change is reworked onto this rule.

### Generation

`update_data.py` already writes the bundled `forms.json` and `counters.json` and a sidecar with the manifest
entry's version and hash. It writes the same for `verbs.json`, `grammar.json`, `furigana.json` and
`words.json` (into the VerbKit resources), and `make data-check` fails if any copy differs from `data/`. The
sidecar for each is `{ "version", "sha256" }` (no `ref`: the app never fetches the bundle).

### Loading

One generic loader reads a bundled file and its sidecar, checks the hash and decodes it, and returns nothing
(never crashes) if anything is missing or does not match. `BundledCounters` becomes an instance of it.

### Per store

- `VerbStore` installs the bundled verbs and grammar before its cached load, so `firstLaunchState` becomes
  `.success` without a download.
- `FuriganaStore`, `WordsStore` and `CountersStore` do the same for their file.
- `DataSyncStatus` shows the bundled version until a sync, as it does for forms.

## Constraints

- The app grows by about 400 KB (verbs 260 KB, grammar 117 KB, furigana 12 KB, words 10 KB), plus the 190 KB of
  counters already added. The widget extension links the same package, so it grows too.
- The bundled copies are generated by `make data`, written byte for byte, and checked by `make data-check` and
  by tests that read the repo's `data/` files.
- Installing the bundle runs once per launch at most and only when it is newer, so a normal launch costs one
  version comparison per file.
- Every `data/` change still has to be re-signed by the owner; the bundled copies are regenerated by the same
  `make data`, and are not part of the signature.

## Delivery

One branch, in this order, each task shipping green: (1) the pipeline writes the four new copies; (2) the
generic loader and the install rule, with tests; (3) `VerbStore` (verbs and grammar), the gate and the status;
(4) furigana, words and the counters rework; (5) the offline check: a build pointed at an unreachable host,
fresh install, every tab and the widgets open.

## Answers a builder will need

From the project as it stands:

- **Two separate records.** The sync state keeps `lastSyncedManifest` (compared by exact version and hash to
  the remote) and `highestAcceptedVersion` (the rollback floor, which survives app updates). Installing the
  bundle writes **both**, and the "is the bundle newer" test is against the floor: install when there is no
  floor, or the floor is older than the bundled version. Equal version is never reinstalled (the pipeline bumps
  the version on any content change), and a bundle older than the floor is skipped, so a restored or sideloaded
  older build can never replace newer data.
- **The six manifest types hold only `version` and `sha256`** (`VerbManifest`, `GrammarManifest`,
  `FuriganaManifest`, `WordsManifest`, `CountersManifest`, `FormsManifest`). `ref` lives in `manifest.json` and
  is not part of the sync state, so an installed bundle compares equal to the same remote entry.
- **The store is shared with the widgets** through the app group `group.dev.martinloeseth.jpverbconjugation`;
  the install is owned by the app. A widget or App Intent that runs before the app has ever launched shows
  its placeholder or nothing until the first launch, which is acceptable: the widget cannot be added before
  the app is installed. The widget extension links the same package, so it carries the resources too.
- **`replaceAllVerbs` deletes, inserts and saves in one context save**, so the existing rule applies unchanged:
  persist first and record the manifest only after the save succeeds. A failed install leaves the old cache
  and records nothing.
- **Integrity.** The sidecar is generated by `update_data.py` from the manifest's entry, and CI
  (`.github/workflows/data.yml`) runs `update_data.py --check` (every bundled copy and sidecar must equal
  `data/` and the manifest) and `sign_manifest.py verify`. So the chain signed manifest, `data/`, bundled copy
  and sidecar is checked on every data change. At run time the loader's hash check catches accidental
  corruption; the bundle itself is protected by the app's code signature.

My calls (the owner can change any of them):

- **Order and gate.** The install runs in each store's `start()` before its cached load, on the main actor,
  as persistence already does. `firstLaunchState` shows `.checking` for that moment and then `.success`; the
  reconnect retry stays for the case where the bundle is missing or corrupt.
- **Stores take the bundle as an optional parameter, default none**, as the counters store does. The existing
  store tests keep testing the no-bundle path (`.failed(.offline)`, `.failed(.serverUnreachable)`); new tests
  cover a store with a bundle.
- **Verbs and grammar are independent.** If verbs install but grammar fails, grammar stays empty until a
  sync, as today (grammar never blocks). If the bundle is corrupt but a cache exists, the cache is used
  silently.
- **Saved references.** Verb and word ids that favourites, the quiz history and the word bank use cannot
  disappear: CI already refuses a published verb id that goes missing. The install replaces the cache the same
  way a sync does.
- **Status.** `DataSyncStatus` records the bundled version with a "bundled" label and no "last synced" time
  until a real sync, so a device that has been offline shows that honestly. Refresh data on a fresh install
  is unchanged.
- **After an offline first launch** a failed background sync is silent, as it is for any launch with a cache.

## Left to the builder

The shape of the install step (a shared helper or one per store), the exact `DataSyncStatus` wording for a
bundled version, and how the sidecar is named.

## Decisions

Decided by the owner on 2026-10-27: (1) **install the bundle into the persisted store**; (2) **committed
generated copies** under the package resources, as forms and counters do; (3) **rework the counters change**
onto the same install rule. The owner approved all of the recommendations below.

## The decisions as put to the owner

1. **Install into the persisted store** (my recommendation) or read the bundle in memory only. In memory only
   is less code but leaves the widgets and App Intents empty until the first download, and needs the bundle
   compared with the cache on every launch.
2. **Generated copies committed under the package resources** (my recommendation, as forms and counters do) or
   symlinks to `data/`. Copies are robust in SwiftPM and Xcode but add about 400 KB of duplicated JSON to the
   repo and to each data diff.
3. **Rework the counters change** onto the install rule (my recommendation), so all six files behave alike.

## As built

Built as designed, in seven tasks on `offline-first-launch`. `update_data.py` writes all six bundled copies and
sidecars (`make data-check` fails on drift); `BundledData<Value>.load(named:)` reads one and rejects a copy
that does not match its sidecar hash; `VerbStore` (verbs and grammar), `FuriganaStore`, `WordsStore` and
`CountersStore` take the bundle as an optional parameter and install it in `start()` before their cached load
when `DataVersion.isNewer(bundled, than: floor)`: persist, then `confirmSynced`, then `recordBundled`. The old
in-memory counters logic (`BundledCounters`, `cacheIsUsable`, the sync service's bundled rules) is gone.
`DataSyncStatus` gained `recordBundled` and `isBundled` (persisted), and Settings > Data shows
"Bundled · v1.13.0" until a sync confirms the version. The app wiring for all six was done in Task 5, since
removing `BundledCounters` broke the build. The Python suite and 1105 Swift tests pass.

**Checked on screen** (iPhone 17 Pro simulator, build pointed at an unreachable host, app uninstalled first):
the app opens to the tabs; the verb table shows with furigana, Grammar lists its points (and Building blocks,
Common mistakes), Counters lists its counters, and Settings > Data shows "Bundled" for verbs, grammar,
furigana and words. Then a normal build, reinstalled: verbs, grammar and words changed to "Version x" once the
server confirmed the same version.

**Install time.** About 20 ms for the verbs and 5 ms for the grammar into an in-memory store on a Mac (65
verbs, 18 grammar points; the plan's "about 1,100 verbs" was wrong). Not measured on a device, but nowhere near
one second.

**Not checked.** The form lookup (the forms catalogue is untouched and was already bundled), the Counters
widget and the other widgets (the simulator cannot easily show them before the app has launched; they read the
same persisted store the install fills), and a first launch on a physical device.

**One consequence worth knowing.** A build whose bundle is newer than what `main` publishes (this branch
carries unmerged counters stage-1 data and a newer furigana) sets the rollback floor above the published
manifest, so the sync of that file is refused as "couldn't be verified" and Settings keeps showing "Bundled".
That is the rollback rule doing its job, and it goes away once the data reaches `main` and is signed. A
released build always ships data that is already published.

**Final review.** An independent review found no critical issues and one important one, fixed: the bundles
for furigana, words and counters waited behind the form catalogue's network sync, so on a weak connection
they could be held back for minutes. Every store now has a synchronous `installBundled()` that the app calls
in `init` before any await (`start()` calls it again and finds nothing to do). Deferred minors: a failed save
is not rolled back in the shared context; every launch reads and hashes all bundles even when nothing is newer
(decode the sidecar first); a floor with an empty store never reinstalls (in-memory fallback); the
`firstLaunchState` wording above; the "Bundled" mark clears when a file has no manifest entry and forms uses
a different call; `docs/security/data-signing.md` does not yet mention bundled copies raising the floor;
orphaned bundled copies are not flagged.
