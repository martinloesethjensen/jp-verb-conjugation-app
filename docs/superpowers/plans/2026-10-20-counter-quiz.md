# Counter Quiz (Milestone 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A counter quiz with two question kinds (*Which counter?* and *Read it*), started from the Counters tab, recorded in the existing quiz history, with Weak spots for counter readings.

**Architecture:** `QuizAttempt.verb` becomes `subject` (a verb id or a counter id) through a SwiftData `originalName` rename. Two new `QuizQuestionKind` cases ride in the same history table; every verb-only consumer (the verb quiz builder, `QuizProgress` weak pairs, the widget) ignores them. Wrong readings used as distractors (さんほん, さんぽん, さっぽん) are generated by `scripts/update_data.py` into `counters.json`, because the app never derives a reading. The quiz runs like the connection quiz: a model class, its own screen, no timer.

**Tech Stack:** Python 3 standard library (data pipeline), Swift 5 mode, SwiftUI (iOS 26), SwiftData, XCTest, `unittest`.

**Spec:** `docs/superpowers/specs/2026-10-17-counters-design.md`, sections "Counter quiz (milestone 2)" and "VerbKit, Milestone 2".

**Base:** `main` with milestone 1 merged. Branch: `claude/counters-quiz`.

## Global Constraints

- Python tests: `cd scripts && python3 -m unittest -v test_update_data test_form_catalogue test_generate_audio` (all must pass). Package tests: `swift test --package-path Packages/VerbKit`; commit only when the **exit code is 0**. Two timing tests (`testSearchStaysFastForFiveThousandEntries`, `testFiveThousandEntriesPlanQuickly`) fail intermittently under load; re-run alone before treating a failure as real.
- After any data edit run `python3 scripts/update_data.py`; then `--check` must print "data is up to date". **Every `data/` change needs the owner to run `python3 scripts/sign_manifest.py sign` before merge.** Never commit a signature yourself; say in the PR that it needs signing.
- After adding app files run `./scripts/generate-project.sh`. iOS build: `xcodebuild -project JPVerbConjugation.xcodeproj -scheme JPVerbConjugation_iOS -destination 'id=<simulator UDID>' -derivedDataPath <scratch>/dd build`. **iPad and macOS checks are parked:** do not build the macOS scheme.
- The app never derives a reading. Quiz choices, answers and explanations come from `counters.json` fields (`readings`, `changed`, `distractors`, `things`). Speech uses the kana reading.
- Multiple choice, no timer. Any accepted reading counts as correct (spec).
- Counter keys (exact): `"1"` … `"10"`, `"what"`. A quiz uses four choices (one right, three wrong) whenever four distinct ones exist.
- Old manifests, old stores and old builds must keep working: an old build skips history rows with an unknown `kindRaw`.
- All new content is written by the assistant and marked unreviewed in the PR.
- Commit messages end with the trailer from the session's attribution reminder.

## Review Focus

Inputs the spec implies but no task's own tests would otherwise cover, most likely to bite first:

1. **Two primary counters for one word** (ビール is 本 and 杯): both are right, and neither is ever offered as a wrong choice. Pinned in Task 4.
2. **The same written form on two counters** (一日 is ついたち on one 日 and いちにち on the other): the prompt must say which counter, or the question has two answers. Pinned in Task 4.
3. **Too few distractors** (a level filter leaves two counters, an irregular counter has no generated wrong readings): the quiz fills from other numbers of the same counter, drops a question rather than show fewer than two choices, and the sheet disables a kind with no questions. Pinned in Tasks 4 and 7.
4. **Existing history survives** the column rename, and rows the old build cannot read are skipped, not crashed on. Pinned in Task 1.
5. **Counter attempts must not reach verb code:** no weak verb pair, no `verb(withID:)` miss in Progress, no widget pick, and no counter kind from the verb quiz builder, while streaks and totals still count them. Pinned in Task 2.

### Task 3: Generate and publish wrong-reading distractors

**Files:**
- Modify: `scripts/update_data.py`, `scripts/test_update_data.py`, `Models/Counter.swift`, `data/counters.json`, `data/manifest.json` (generated)
- Test: `scripts/test_update_data.py`, `Packages/VerbKit/Tests/VerbKitTests/CounterDecodingTests.swift`, `RealCountersDataTests.swift`

**Interfaces:**
- Produces (Python): `counter_distractors(counter, readings) -> dict[str, list[str]]`; `apply_counter_readings` also sets each counter's `distractors`; `check_counters` rejects a distractor that is not hiragana or that equals an accepted reading of its key.
- Produces (Swift): `Counter.distractors: [String: [String]]` (`decodeIfPresent ?? [:]`), `Counter.distractors(for: CounterNumber) -> [String]`.

Distractor rules, tried in this order per key, keeping the first three distinct results that are not accepted readings of that key:
1. *Unchanged:* the base number plus the counter's reading (さんほん).
2. *Neighbour:* for `h-b` and `h-p`, the preferred reading with ぱ-row and ば-row swapped (さんぼん → さんぽん; さんぷん → さんぶん). For the other classes, the base number's last kana replaced by small っ plus the reading (さんこ → さっこ), skipped when the preferred reading already has that shape.
3. *Misplaced っ:* the base number's last kana replaced by small っ plus the counter's reading, with its は-row sound turned to the ぱ row for `h-b`/`h-p` (さっぽん). Skipped when equal to an earlier candidate.
Irregular counters get only rule 1. A key may end up with fewer than three; the app fills the rest (Task 4).

- [ ] **Step 1: Write the failing Python tests** with hand-written expected values: 本 at `"3"` → `["さんほん", "さんぽん", "さっぽん"]`; 本 at `"1"` (preferred いっぽん) → `["いちほん", "いっぼん"]` (rule 3 equals the preferred reading and is dropped); 分 at `"3"` (preferred さんぷん) → `["さんふん", "さんぶん", "さっぷん"]`; 枚 at `"3"` → `["さんまい", "さっまい"]`; 人 at `"4"` → `["よんにん"]`; `check_counters` flags `distractors` equal to an accepted reading; `--check` reports a counters file with missing `distractors` as stale.
- [ ] **Step 2: Run them to verify they fail.**

### Task 4: Build counter questions

**Files:**
- Create: `Quiz/CounterQuestion.swift`
- Test: `CounterQuestionTests.swift`

**Interfaces:**
- Consumes: `Counter`, `CounterNumber`, `Counter.distractors(for:)`, `Counter.thingsByFit`, `CounterGroup`.
- Produces:

```swift
public struct CounterQuestion: Equatable, Sendable, Identifiable {
    public var id: UUID
    public var kind: QuizQuestionKind        // .counterChoice or .counterReading
    public var counterID: String             // attempt subject
    public var formID: String                // counterChoice: the thing's word; counterReading: the number key
    public var prompt: String                // "傘" or "三本"
    public var detail: String                // "umbrella" or the counter's meaning ("day of the month")
    public var symbol: String?               // the thing's symbol, counterChoice only
    public var correct: String               // the counter ("本") or the preferred reading ("さんぼん")
    public var accepted: Set<String>         // every right choice; always contains `correct`
    public var choices: [String]             // shuffled; one or more accepted, the rest wrong
    public var explanation: String           // shown after a wrong answer
}

public func buildCounterQuestions(
    counters: [Counter], groups: [CounterGroup], kind: QuizQuestionKind, count: Int
) -> [CounterQuestion]

/// Questions about one counter (Practise this counter): .counterReading only.
public func buildCounterQuestions(for counter: Counter, count: Int) -> [CounterQuestion]
```

Rules:
- *Which counter?* One question per distinct thing word. Accepted = every counter listing the word with fit `primary`, and if none is primary, the counters with the best fit present. A thing whose accepted counters are only `casual` (つ, 個 fallbacks) makes no question. Wrong choices come from counters that do not list the word at all, those sharing a group with an accepted counter first, then the rest in input order; three of them.
- *Read it.* One question per (counter, number key) where the counter has at least one wrong choice available. Prompt is `counter.written(number)`; detail is `counter.meaning`. Accepted = all of `counter.readings(for:)`. Wrong choices: `counter.distractors(for:)` first, then the preferred readings of other numbers of the same counter in key order starting from the nearest, none equal to an accepted reading; three of them. Fewer than one wrong choice drops the question.
- Explanation, wrong *Read it* answer: for a counter with a non-empty `changed`, "本 changes at 1, 3, 6, 8, 10 and 何: さんぼん" (numbers from `changed`, the right reading last); for `irregular`, "つ is irregular: learn each reading. 三つ is みっつ"; otherwise "枚 has no sound changes: さんまい". Wrong *Which counter?*: "傘 is counted with 本 (long, thin things)", listing every accepted counter.
- Questions are shuffled; `count` caps the result; the order is deterministic under a seeded generator parameter only if the existing builders do the same, otherwise plain `shuffled()`.

- [ ] **Step 1: Write the failing tests** on a fixture of 本, 杯, 匹, 羽, 人, つ and the two 日 counters:
  - ビール (primary under both 本 and 杯) gives one question whose `accepted == ["本", "杯"]`, and neither 本 nor 杯 appears among its wrong choices. *(Review Focus 1)*
  - うさぎ (acceptable under 匹, primary under 羽) accepts 羽 only and never offers 匹 as a wrong choice.
  - a thing listed only as `casual` makes no question.
  - 三本 gives `correct == "さんぼん"`, `choices` containing `さんほん`, `さんぽん` and `さっぽん`, four choices in all, `explanation` starting "本 changes at 1, 3, 6, 8, 10 and 何".
  - 八本's `accepted == ["はっぽん", "はちほん"]`; no wrong choice equals either.
  - the two 日 counters at 一日: both questions exist, their `detail`s differ ("day of the month" vs "number of days"), and the `accepted` sets are `["ついたち"]` and `["いちにち"]`. *(Review Focus 2)*

  - with only two counters passed in, *Which counter?* questions have two choices; with one counter, no questions. *(Review Focus 3)*
  - `kind` is `.counterReading` for read-it questions, `.counterChoice` for the other; `formID` is the number key / the thing's word.
